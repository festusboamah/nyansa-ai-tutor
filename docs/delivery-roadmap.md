# Delivery Roadmap

This roadmap replaces the previous "full school operating system" phase plan (Phases 1–8 of that plan are preserved in git history and summarized under "Prior roadmap" below — nothing they built has been deleted). It follows the 2026 strategic reset: see [`product-boundary.md`](product-boundary.md) for why, and [`repository-audit.md`](repository-audit.md) for the per-app classification referenced throughout.

## Phase 0 — Product boundary & repository audit

**Goal:** Freeze scope creep into school-ERP territory and classify existing code before changing anything.

Deliverables:

- Product-boundary document and per-app repository audit.
- `AGENTS.md` rules so coding agents don't extend the frozen apps.
- This roadmap rewrite.

Exit criteria:

- No new feature crosses the agreed Nyansa/Suku360 ownership boundary.
- Existing production-capable work (including `attendance`, `finance`, `guardians`, `reports`, `communications`) is not destroyed during separation.

**Status: complete.** `product-boundary.md`, `repository-audit.md`, and `AGENTS.md` are in place. No application code was touched.

## Phase 1 — Learning core consolidation

**Goal:** Strengthen subjects, materials, quizzes, assignments, exams, and teacher/student workflows; move to production-grade infrastructure.

Deliverables:

- Strengthen `academics`, `courses`, `quizzes`, `gradebook` — unify learning-activity and assessment evidence models.
- Improve teacher workflows and student dashboards.
- Content permissions, versioning, and audit where required.
- Move production deployment to PostgreSQL and production-grade media/object storage.

**Status: largely satisfied.** `academics`, `courses`, `quizzes`, and `gradebook` are built and tested (`gradebook` alone has an 829-line test suite covering entry, review, revision, and import). The PostgreSQL half of the infra deliverable is done: `config/settings.py::database_from_url` parses `DATABASE_URL` into a real Postgres config, `Dockerfile`/`render.yaml` deploy against a managed Postgres instance, and `.github/workflows/ci.yml` runs the full test suite against real PostgreSQL 17 on every push plus a production-release rehearsal (`migrate` → `collectstatic` → `production_check`) — SQLite is intentionally dev-only. Still open: production-grade object storage for uploaded media (currently local `FileSystemStorage`) — already tracked as a manual external gate in `docs/production-readiness.md` ("provision persistent private media storage... Render's service filesystem is ephemeral") rather than a code task, and not yet worth building since this project's only live deployment is an explicitly demo-only Render instance.

## Phase 2 — Nyansa Tutor 2.0

**Goal:** Curriculum/context-aware tutoring with explicit pedagogical modes, not answer dumping.

Deliverables:

- Curriculum/context-aware tutoring, grounded in approved materials.
- Guided explanations and progressive hints rather than direct answers.
- Practice-question generation with difficulty controls.
- Conversation safety, age-appropriate behaviour, teacher/school controls.
- Usage/cost limits and observability.

**Status: all 8 modes shipped, all 9 teacher/school controls shipped.** (Correcting an earlier miscount in this doc: the source roadmap lists 9 distinct controls — mode selection, allowed materials, topic focus, difficulty range, hint depth, final-answer reveal, assessment-period restrictions, review requirement, and cost policy — not 7.) The `tutor` app delivers a real conversational tutor: `TutorSession`/`TutorMessage` models with proper multi-turn Claude conversations (not the single-shot-with-concatenated-history pattern `study_ai.py` uses), a mode registry (`tutor/modes.py`) covering all eight roadmap modes — **Teach Me, Guide Me, Give Me a Hint, Practice With Me, Check My Work, Explain My Mistake, Revise With Me, Exam Mode** — optional grounding in a student's uploaded `courses.StudyDocument`, and a `TutorUsageEvent` log per Claude call (model, tokens, success/failure) satisfying the "usage/cost... observability" exit criterion. AI failures degrade to a fallback message instead of breaking the chat.

Two of the new modes have real behavior beyond a new prompt: **Exam Mode** never calls Claude at all — it short-circuits in `tutor/engine.py` to a fixed message pointing the student to `quizzes` for the actual timed/controlled assessment, so the AI can never assist during a graded attempt. **Revise With Me** is the first live integration between Tutor (Pillar A) and Mastery (Pillar D): when a subject is set, the engine pulls the student's `NEEDS_SUPPORT`/`DEVELOPING` topics from `mastery.services.student_subject_mastery` and prioritizes them in the system prompt.

Teacher/school controls: a school-level `TutorSettings` model covers three — admins can disable specific modes (`tutor/views.py::available_modes`, enforced both in the mode picker and against direct POSTs to start a session), cap how many progressive hints Give Me a Hint gives before stopping (`max_hint_depth`, counted from the session's own `TutorMessage` history — no new model needed), and toggle whether the tutor may reveal a final answer once that hint limit is reached (`allow_final_answer_reveal`; when off, `tutor/engine.py` short-circuits with no Claude call at the limit, mirroring how Exam Mode short-circuits). Two more are session-level, not school-level: a session can now ground in a teacher-approved `courses.Material` instead of only a student's self-uploaded, ungoverned `StudyDocument` — `Material` is teacher-curated by construction (only teachers/admins can create it), so no separate approval flag was needed, just the ability to ground in it at all (`courses.study_ai.get_or_extract_material_text` lazily extracts and caches text on first use, and takes precedence over a study document when both are set); and a session can optionally focus on one `mastery.Topic`, with the engine instructing the AI to stay on it or suggest a new session. The cost-policy control is also now real enforcement, not just logging: `TutorSettings.daily_usage_limit` caps how many tutor Claude calls a school can make per day (school-wide, not per-student — counted from the existing `TutorUsageEvent` rows, no new counter model); once hit, `tutor/engine.py` short-circuits with a fixed message and no Claude call, same pattern as Exam Mode and the hint-depth limit. Difficulty range is the seventh: `TutorSettings.min_difficulty`/`max_difficulty` (reusing the exact `easy`/`medium`/`hard` scale `quizzes/forms.py::QuizGenerationForm` already defines) bound how hard `PRACTICE`-mode questions can get; the engine only adds guidance to the prompt when the configured range is narrower than the full scale, and — like topic focus and the "never reveal the answer" instructions elsewhere — this is prompt guidance an AI is asked to follow, not a hard, verifiable constraint (unlike hint depth and the usage quota, which are countable and enforced without relying on the AI). The eighth is assessment-period restrictions: `TutorSettings.restricted_period_start`/`restricted_period_end` let an admin block the tutor school-wide for a date range (e.g. exam week), distinct from the existing per-session `EXAM_MODE` (a student's own opt-in controlled attempt) — this is a blanket blackout checked first in `tutor/engine.py::send_message`, before mode-specific logic, hint state, or the usage quota, since it's a broader "is the tutor available at all today" gate.

The ninth and last, review requirement, lives outside `tutor` entirely — it required auditing where AI-generated content actually reaches students unreviewed. Three of the four candidates turned out already compliant: lesson notes already have a full `DRAFT → PENDING_REVIEW → SENT_BACK → APPROVED` workflow (`dashboard/models.py::LessonNote`, `dashboard/lesson_workflow.py`); AI-assisted assignment grading is review-by-design (`AssignmentSubmission.ai_suggested_score`/`ai_suggested_feedback` are separate from the authoritative `final_score`/`teacher_feedback` a teacher sets); and the Self-Study Hub is a private, single-student tool with no other-student or teacher visibility, so review doesn't apply. The actual gap was AI-generated quizzes: `ai_generate_quiz_view` created live `Quiz`/`Question`/`Choice` rows immediately, with no status field and no approval step, so any enrolled student could take one the instant it was generated. Fixed with `Quiz.status` (`DRAFT`/`PUBLISHED`, defaulting to `PUBLISHED` so manually-created quizzes via `create_quiz_view` are unaffected) and a new `QuizGenerationSettings.require_review` (defaulting to `True` — the opposite convention from `TutorSettings`, since this closes an actual safety gap rather than adding an optional restriction): an AI-generated quiz now starts as `DRAFT` unless a school has opted out, `quiz_start_view` rejects students from an unpublished quiz, a new `publish_quiz_view` lets the owning teacher publish it, and `courses/views.py::subject_detail_view` excludes draft quizzes from what students (not teachers) see listed.

Persisted misconception tracking for Explain My Mistake — the one remaining item from the original Tutor 2.0 deliverable list — is now shipped too. `mastery.Misconception` (Pillar D territory, same reasoning as `Strand`/`Topic`) persists the AI's already-conversational hypothesis verbatim: no new AI call, no structured-output parsing. It's **one record per session, not per message** — `tutor/engine.py` calls `Misconception.objects.update_or_create(source_session=session, ...)` after a *successful* `EXPLAIN_MY_MISTAKE` reply (a `source_session` `OneToOneField` enforces this), so follow-up clarifying turns in the same conversation update the hypothesis rather than piling up near-duplicate rows, and a failed AI call creates nothing. Every record carries `student_description` (what the student said went wrong) alongside `hypothesis` (the AI's reply) — the evidence is never separated from the claim. `status` (`OPEN`/`DISMISSED`/`RESOLVED`) is deliberately left out of the `update_or_create` defaults, so a teacher's dismiss/resolve call on an earlier hypothesis can't be silently reset by a later message in the same session. New `mastery/views.py::misconceptions_view` (teacher/admin, `can_view_class`-gated, reached via a link from the class mastery page) lists a class's `OPEN` misconceptions with `Dismiss`/`Resolve` actions — matching "teachers retain control" and "a single wrong answer should not normally create a persistent misconception label" by keeping every hypothesis an explicit, overridable claim rather than an auto-confirmed diagnosis. Misconception *pattern detection* across sessions (e.g. flagging a recurring misconception) remains out of scope — that's the roadmap's separate, bigger Misconception Engine work.

The six pre-existing single-shot AI call sites (`study_ai.py`, `ai_quiz_generator.py`, `ai_grading.py`, `assignment_ai.py`, `lesson_ai.py`, `ai_reports.py`) have been migrated onto shared plumbing (`ai_core/client.py`) — one Claude client instantiation, one JSON-fence-stripping implementation, and consistent `AIError` handling instead of six duplicated, inconsistent copies. `dashboard/ai_reports.py::generate_student_report` previously had no error handling at all (an API failure would 500 the request) and now degrades gracefully like the other five. `tutor/engine.py` keeps its own separate error handling (multi-turn conversation + DB usage logging is a different shape) and was not migrated onto `ai_core`.

## Phase 3 — Mastery engine

**Goal:** Explainable mastery evidence and misconception detection from learning activity.

Deliverables:

- Topic/strand/outcome taxonomy.
- Map learning activities to outcomes.
- Compute explainable mastery evidence from attempts and teacher-approved work.
- Identify misconceptions and learning gaps; show learner/teacher progress views.

**Status: all deliverables shipped, including every item from the fuller roadmap vision — taxonomy, question-level mastery, misconception pattern detection, prerequisite/concept modeling, and curriculum pack versioning.** `analytics` no longer depends on `attendance` or `reports` (see audit doc). A new `mastery` app adds a two-level taxonomy (`Strand` → `Topic`, scoped to `courses.Subject`) and mastery evidence computed from both assessment- and question-level sources: each `gradebook.Assessment` and each `quizzes.Question` can be tagged with one `Topic`, and `mastery.services.topic_mastery_for_student` blends published+approved `GradeEntry` scores with per-question `Answer.is_correct` results (for quizzes linked to a term-scoped gradebook assessment) into one bucketed mastery percentage — Mastered/Developing/Needs Support/No Evidence (matching the roadmap's Learning Evidence Passport language), with evidence count, per-source evidence counts, and period stated on every indicator. Student and teacher/admin dashboards, plus admin curriculum management, are live at `/mastery/`.

(Correcting an earlier miscount in this doc: question-level tagging had already shipped when this line previously said "still open" — `quizzes.Question.topic` and the `Answer.is_correct` blending in `topic_mastery_for_student` predate this correction.)

Misconception pattern detection — the last genuinely open item from this phase — is now shipped too. Earlier this session's persisted-misconception-tracking work made `mastery.Misconception` durable but strictly per-session (`tutor/engine.py::_record_misconception` keys `update_or_create` only on `source_session`, never on `(student, topic)`), so nothing prevented — or surfaced — the same student getting flagged on the same topic across multiple sessions, or several students independently getting flagged on the same topic in one class. New `mastery/services.py::misconception_patterns(school_class, term)` groups a class's `OPEN` misconceptions by topic (reusing the same roster-scoping idiom `misconceptions_view`/`class_topic_bands` already use) and surfaces only genuine patterns — a topic with 2+ distinct affected students, or one student recurring 2+ times on it — added directly into the existing `misconceptions_view`/`misconceptions.html` as a new "Recurring Patterns" section above the unchanged flat list, no new URL or permission logic. Deliberately structural, not semantic: this codebase has no embeddings/clustering capability anywhere (`ai_core/client.py` only exposes single-shot `complete_text`/`complete_json`), so "pattern" means topic-based grouping, not comparing what two different AI hypotheses actually mean — building real NLP clustering was explicitly out of scope for this pass, as was any automatic action (e.g. auto-creating a `RemediationPlan`) when a pattern is detected, keeping with this session's "system computes, a person decides" discipline.

Prerequisite/concept modeling closes the last-but-one item. Genuinely new territory — confirmed by exploration before building it: no self-referential/graph pattern existed anywhere in the codebase, and `Topic.order`/`Strand.order` never carried sequencing weight (pure display sort). New `Topic.prerequisites` is a plain self-referential `ManyToManyField("self", symmetrical=False, related_name="unlocks")` — no through-model, since nothing in the stated use case needs per-edge metadata, matching this codebase's established "thin models, logic in services.py" style. `mastery/services.py::add_topic_prerequisite(topic, prerequisite)` guards against both a topic requiring itself and any indirect cycle (`_creates_cycle` walks the existing prerequisite graph via DFS before every add — the one place a graph structure needed real validation logic this codebase hasn't needed before, since M2M edges can't be validated inside `Model.clean()` before the object has a PK). Wired into exactly one consumer for this pass — `differentiated_tasks_view`, already the page where a teacher reads "this student is `NEEDS_SUPPORT` on Fractions" and decides what to do about it: a new `unmet_prerequisites(student, topic, term)` call surfaces a "may actually need: Whole Numbers (Needs Support)" note right there when a struggling student also hasn't mastered a prerequisite, the roadmap's own "the real gap might be upstream" framing turned into a direct query rather than a manual guess. Curriculum admins manage the graph on the existing `curriculum_view`/`curriculum.html` page (new `add_prerequisite`/`remove_prerequisite` actions, same one-view-many-actions pattern established throughout `mastery` this session) — no bulk import, no AI-suggested edges, no graph visualization; one edge at a time, matching how `Strand`/`Topic` themselves are already curated. Deliberately not wired into `tutor/engine.py`'s difficulty logic or `study_goals_view` — both plausible, both a real behavior change (redirecting a session or goal toward a different topic) beyond what a first pass needs.

Curriculum pack versioning closes Phase 3 entirely — and was the least-specified item ("curriculum pack versioning" appears exactly once in this whole doc, with no elaboration anywhere else to recover; confirmed by search before building anything speculative). Rather than invent a "TopicVersion snapshot" system nothing currently needs (mastery evidence is always computed live from `GradeEntry`/`Answer`, never stored, and nothing needs "what did the curriculum look like last term" reporting), this scoped around a concrete risk exploration surfaced in the actual schema: `RemediationPlan.topic` and `StudyGoal.topic` were the only two topic-tag FKs in the codebase set to `on_delete=CASCADE` — every sibling (`Assessment.topic`, `Question.topic`, `BankQuestion.topic`, `Misconception.topic`, `TutorSession.topic`) is `SET_NULL`. Deleting a `Topic` silently destroyed every remediation plan and study goal ever created for it, including a completed plan's `mastery_percentage_at_start`/`_at_completion` — the exact records `remediation_plan_outcomes`'s improvement-rate analytics depend on. Both are now `SET_NULL` (`null=True, blank=True`), matching every sibling — a real inconsistency fixed, not a hypothetical one. Separately, `curriculum_view` (the app's own admin UI) had no edit path at all — every POST branch only ever `INSERT`ed a new `Strand`/`Topic`; the only way to rename or re-parent an existing topic was Django's built-in admin, unguarded and untracked, silently rewriting what every live-rendered historical mastery view shows (nothing snapshots a topic's name at evidence-recording time). New `mastery.TopicRevision` is `gradebook.GradeEntryRevision`-shaped — the codebase's own established "what changed and when, for an already-graded record" pattern, applied to `Topic` instead: `topic = ForeignKey(..., on_delete=PROTECT)` (once a topic has been edited even once, it can't be deleted at all without deleting its history first — the same choice `GradeEntryRevision.entry` already makes), previous/new name and strand stored as plain value fields rather than FKs (mirroring how `GradeEntryRevision` stores old/new *values*, not references that could themselves drift), and `save()`/`delete()` overrides that raise if the row already has a PK — immutable by construction. New `mastery/services.py::update_topic(*, topic, actor, name, strand, reason)` (`gradebook/history.py::record_grade_entry`-shaped: keyword-only, `actor`+`reason` required, atomic) is the only sanctioned way to edit a topic in app code, wired into a new `curriculum_view` `edit_topic` action — the first time the app's own UI could rename a topic at all, and the only path that produces a revision row. Deliberately out of scope: locking down Django admin's missing school-tenant scoping (a real, separate gap — no `ModelAdmin` anywhere in this codebase enforces it, not specific to `mastery`, flagged but not fixed here); versioning `Strand` itself (scoped to `Topic` only, the entity evidence/plans/goals actually key off); and any delete path in the app's own UI (deletion stays exactly as reachable as before — this pass makes it *safe*, not newly exposed).

## Phase 4 — Personalised learning paths

**Goal:** Evidence-based revision and remediation recommendations.

Deliverables: adaptive practice difficulty, teacher-approved remediation plans, student study goals and spaced revision, measured improvement after recommended activities.

**Status: all 4 deliverables shipped — adaptive practice difficulty, teacher-approved remediation plans, student study goals and spaced revision, and measured improvement reporting.**

Tutor Practice With Me mode's difficulty used to be entirely static: `tutor/engine.py::_difficulty_range(session)` turned the school-admin-configured `TutorSettings.min_difficulty`/`max_difficulty` band into one fixed sentence of prompt guidance, the same for every student regardless of how they were actually doing. Meanwhile a PRACTICE session already optionally carries a `mastery.Topic` (student-selectable when starting a session, via `start_session_view`'s existing `topic_id` field), and `mastery.services.topic_mastery_for_student(student, topic, term)` — computing exactly the per-student, per-topic mastery band needed — was never called from `tutor` at all; only the whole-subject aggregate `student_subject_mastery` was, and only for Revise With Me mode. This slice wires that unused connection: `_difficulty_range` now calls a new `_mastery_target_difficulty(session, min_difficulty, max_difficulty)` helper (mirroring `_mastery_context`'s exact `SchoolMembership` lookup and "current term" convention, same bare-except fail-safe) that maps the student's mastery status on the session's topic to a target difficulty (`NEEDS_SUPPORT`→Easy, `DEVELOPING`→Medium, `MASTERED`→Hard), then **clamps** that target within the school's configured `[min_difficulty, max_difficulty]` range using a `DIFFICULTY_ORDER` list (moved from `tutor/views.py`, where it was previously only used to validate an admin's range, into `tutor/models.py` next to `DifficultyLevel` so both places can share it) — the admin's range is a ceiling/floor the mastery-derived target clamps into, never a hint it can bypass. A topic-less PRACTICE session, or one with no recorded mastery evidence yet (`NO_EVIDENCE`), falls through unchanged to the original static-range sentence (or no guidance at all, for the default full range) — verified by the existing `DifficultyRangeEngineTests` suite passing untouched, since all four of those tests exercise topic-less sessions.

Deliberately out of scope for this slice: adaptive difficulty for `quizzes.BankQuestion`/quiz-taking — there is currently no student-facing "give me practice questions from the bank" flow at all (bank→quiz assembly is teacher-only, via `add_bank_questions_view`), so extending adaptivity there is new surface area for a future slice, not a wiring job like this one; and unifying `tutor.DifficultyLevel`/`quizzes.BankQuestion.Difficulty` into one shared enum (they already have identical string values, and merging them is an unrelated cleanup with its own risk).

Slice 2, teacher-approved remediation plans, is deliberately built as a mastery-native concept rather than an extension of Phase 8's existing `analytics.Intervention`/`RiskSignal` early-warning system — confirmed by design, not just by name, to be the right split: `RiskSignal` is hard-wired to `EarlyWarningPolicy` (a mandatory, non-nullable `policy` FK; academic-average/submission-rate/missing-grades thresholds only) with no `topic` field anywhere in that chain, so a mastery-topic gap can't be represented there without an invasive migration to a model whose whole shape is "policy threshold breach," not "topic gap." New `mastery.RemediationPlan` (`school`, `student`, `topic`, `term`, `plan` text, `status` `ACTIVE`/`COMPLETED`/`CANCELLED`, `mastery_percentage_at_start`/`mastery_percentage_at_completion`, `outcome`, `created_by`, timestamps) is `Misconception`-shaped instead — the same per-student/per-topic staff-reviewed record pattern already established in this app, keyed on `(student, topic, term)` rather than a policy-threshold signal. It's deliberately simpler than `Intervention`: no separate `owner` distinct from `created_by` (reassigning a plan to a different teacher is out of scope for this pass).

There was also no page anywhere that showed one individual student's mastery on one topic to a teacher with an obvious "act on this" button — the closest thing was `mastery/views.py::differentiated_tasks_view` (already built two slices ago), which buckets a class roster into `NEEDS_SUPPORT`/`DEVELOPING`/`MASTERED`/`NO_EVIDENCE` per topic and renders each student's name + percentage. Rather than build a new page, plan creation/completion/cancellation was added directly into that view as three more `action=` POST branches (`create_plan`/`complete_plan`/`cancel_plan`), exactly the same "one view, multiple actions, already-authorized by the existing `@mastery_staff_required` + `can_view_class` gate" pattern `misconceptions_view` and `bank_review_queue_view` already established — no new permission logic needed anywhere. Scoped to the `NEEDS_SUPPORT` band only (remediation addresses a gap; the `MASTERED` band already has its own extension-practice generation from the differentiated-tasks slice). `mastery_percentage_at_start`/`mastery_percentage_at_completion` are a light, per-plan version of Phase 4's separate "measured improvement" deliverable: the view already has to call `topic_mastery_for_student` at exactly those two points anyway (once to decide which band a student is in, once to know current mastery when completing a plan), so capturing a before/after number is essentially free — this is not the fuller cross-plan improvement reporting/dashboard that deliverable implies, which stays its own future slice.

Slice 3, student study goals and spaced revision, was genuinely new territory (repo-wide search found no goal/reminder/spaced-repetition concept anywhere) but was built almost entirely by wiring three existing pieces together rather than inventing a parallel system: `mastery.Topic`/`topic_mastery_for_student` for how weak a student is, `tutor.TutorSession.created_at` (sessions already carry a nullable `topic` FK, so "when did this student last work on this topic" is a one-line query) for staleness, and the existing `tutor_start_session` POST endpoint with `mode=REVISE_WITH_ME` for the actual revision action — zero new `tutor`-side code needed at all. New `mastery.StudyGoal` (`student`, `topic`, `note`, `status` `ACTIVE`/`ACHIEVED`/`ABANDONED`) is deliberately the same thing the spaced-revision list tracks, not two separate features — a student sets a goal on a topic, and `mastery/services.py::goal_revision_status(goal, term)` reports whether it's `due` (a fixed `REVISION_DUE_AFTER = timedelta(days=7)` staleness threshold, not a real SM-2/Leitner scheduling algorithm — deliberately simple) alongside current mastery and last-studied time. New `mastery/views.py::study_goals_view` (URL `mastery_study_goals`) is student-only, one view with `create`/`achieve`/`abandon` POST branches matching this session's now-standard pattern, reached via a new student nav link and a small "N topic(s) due for revision" card added to `courses/views.py::dashboard_view` — the actual page students land on via the nav "Dashboard" link (confirmed via exploration to be `courses.dashboard_view`/`templates/courses/student_dashboard.html`, not the similarly-named `dashboard` app, which is 100% teacher/admin lesson-note workflow despite the name). Achieving a goal is always a manual, student-initiated action — mastery crossing `MASTERED` never auto-completes a goal, matching `Misconception`/`RemediationPlan`'s existing "system computes, a person decides" pattern. `courses` importing from `mastery.services` for the dashboard card is a new import direction for that specific app, but not a new *kind* of coupling — `tutor`, `quizzes`, and `analytics` already read `mastery` data the same way, `courses` doing it too for an at-a-glance nudge follows the same established one-directional "keep-side apps read mastery evidence, mastery doesn't reach back" shape. Deliberately out of scope: real spaced-repetition scheduling, push/email reminders (in-app only — this session has consistently avoided adding any new `communications` import, and reminders here don't need one), and a school-configurable staleness threshold (the 7-day window is a hardcoded constant for this pass).

The fourth and final slice, measured improvement reporting, closes the loop on the before/after snapshots slice 2 already captures but never rolled up anywhere: `RemediationPlan.mastery_percentage_at_start`/`mastery_percentage_at_completion` existed since that slice shipped, but a teacher could only ever see one plan at a time, never "did remediation actually work this term." New `mastery/services.py::remediation_plan_outcomes(school_class, term)` and `remediation_plan_outcomes_for_classes(classes, term)`/`school_remediation_plan_outcomes(school, term)` are deliberately `class_metrics`/`school_metrics`-shaped (same `period`/`source`/count/`Decimal`-quantized-rate convention `analytics/services.py` already established) — new `mastery/views.py::improvement_report_view` (URL `mastery_improvement_report`) mirrors `analytics.dashboard`'s exact admin-vs-teacher branching (admin sees the school-wide rollup, a teacher sees only classes they're `class_teacher` of or hold a `TeacherAssignment` for, the same `Q` filter `mastery_overview_view`'s own teacher branch already uses). A `COMPLETED` plan's two mastery snapshots can each independently be `None` (a student can legitimately have zero evidence at either point in time — `NO_EVIDENCE` is a real, non-error bucket, not missing data to paper over), so the report explicitly separates `completed_count` from `comparable_count` (both snapshots present) and only computes `improvement_rate` over the comparable subset, `None` rather than `0` when nothing is comparable yet — never guessing at a number that wasn't actually measured. Deliberately scoped to `RemediationPlan` only, not `StudyGoal`: `StudyGoal` has no mastery-percentage field and never captured one at creation time, and `topic_mastery_for_student` is a live, current-state-only computation with no historical/as-of-date query path, so there is no honest way to reconstruct "what was mastery when this goal was set" after the fact — fabricating that comparison would be the same kind of unsupported inference `NarrativeSnapshot`'s own prompt already explicitly forbids ("do not infer causes"). Out of scope: CSV/PDF export (the `attendance/views.py::attendance_summary_csv` pattern is available to reuse later if wanted, but wasn't needed to deliver the report itself), and retroactively backfilling snapshots for plans that predate the remediation-plans slice.

**Phase 4 (Personalised Learning Paths) is now fully shipped** — all 4 deliverables from the source roadmap (adaptive practice difficulty, teacher-approved remediation plans, student study goals and spaced revision, and measured improvement reporting) are built, tested, and documented.

## Phase 5 — Teacher Copilot 2.0

**Goal:** Curriculum-aligned lesson/resource generation and feedback assistance.

Deliverables: differentiated tasks, rubric/feedback assistance, question-bank generation and quality review, teacher insight summaries grounded in visible metrics.

**Status: all 4 deliverables shipped — question-bank generation/quality review, differentiated tasks by mastery level, rubric/feedback assistance, and teacher insight summaries.** A baseline exists in `dashboard` (`lesson_ai.py`, `ai_reports.py`) for lesson-note generation and AI report drafting, but no rubric/feedback, differentiation, or question-bank code existed anywhere before this pass.

The question bank lives in `quizzes`, not `dashboard` — it's a variant of the AI question generation `ai_generate_quiz_view` already does, not a lesson-note-style workflow. The key difference from that existing flow: `ai_generate_quiz_view` generates questions straight into one specific live `Quiz`, used once. A bank question is a reusable template a school builds up over time: `BankQuestion`/`BankQuestionChoice` (`quizzes/models.py`) store AI-generated questions independently of any quiz, tagged with `subject` and an optional `mastery.Topic`, calling the same `ai_quiz_generator.py::generate_quiz_questions` the quiz flow already uses. Every bank question starts `PENDING_REVIEW` — mirroring the `Quiz.status` draft/publish gate in spirit, but a genuinely separate mechanism: that gate governs whether an AI-*generated quiz* is visible to students, while this one governs whether an individual *bank question* is trusted enough to ever be reused at all, decided once at bank-entry time rather than per quiz. `bank_review_queue_view` (teacher or admin, same `reviewed_by`/`reviewed_at` pattern `mastery.Misconception`'s review flow already uses, down to reusing `request.school_membership` as the reviewer) lets a reviewer approve or reject each one with an optional note; rejected questions are kept, not deleted, for audit.

Only `APPROVED` bank questions are selectable. Because `Question.quiz` is a required FK — a live question belongs to exactly one quiz by design — reusing a bank question across many quizzes means *copying* it, not sharing the row: `add_bank_questions_view` lets the quiz-owning teacher pick from the approved bank questions in their quiz's subject and copies each selected one into new `Question`/`Choice` rows on that quiz, leaving the original bank question untouched and still selectable for the next quiz. This has no interaction with the `Quiz.status`/`QuizGenerationSettings.require_review` gate from Phase 2 — the bank questions being added were already reviewed once at bank-entry time, so adding them doesn't reopen quiz-level review.

The third slice, differentiated tasks, connects this bank straight to Phase 3's mastery evidence rather than adding a second content system. `mastery/views.py::class_detail_view` only ever showed one *aggregated* percentage per topic for a whole class (`class_topic_mastery` mixes every roster student's evidence into a single number) — there was no view anywhere that grouped individual students by mastery band for a topic. New `mastery/views.py::differentiated_tasks_view` (reached via a "Differentiate" link added to each topic row on the class mastery page) fills that gap: it loops the class roster through the existing `topic_mastery_for_student(student, topic, term)` — unchanged, just called once per roster member instead of once for the whole class — and groups the results into `MASTERED`/`DEVELOPING`/`NEEDS_SUPPORT`/`NO_EVIDENCE` lists. From there, a one-click form per populated band (`NO_EVIDENCE` has no form — there's no mastery signal to size a difficulty from) generates a right-sized `BankQuestion` set for that group: `NEEDS_SUPPORT`→`easy`, `DEVELOPING`→`medium`, `MASTERED`→`hard` (extension/challenge), reusing the exact same `PENDING_REVIEW` bank pipeline slice 1 shipped — no separate review mechanism, no new model, no migration. The shared "call the AI, then persist `BankQuestion`/`BankQuestionChoice`" logic was extracted out of `generate_bank_questions_view` into `quizzes/ai_quiz_generator.py::create_bank_questions(subject, topic, difficulty, topic_description, num_questions, created_by)` so both entry points — the plain generator form and this mastery-aware one — produce identically-shaped, identically-reviewed bank questions; the view rejects generation for a band with zero current students (checked server-side against the same freshly-computed bands, not just hidden in the UI) rather than silently generating for nobody. Deliberately out of scope for this slice: free-text/project-style differentiated tasks (`quizzes.Assignment` has neither a `topic` nor a `difficulty` field today, so it isn't a fit as-is), a formal `MasteryLevel` enum (the four bands stay the same string literals `mastery.services._bucket` already returns everywhere else), and automated per-student delivery (getting a generated set in front of the right students is still the same manual "add from bank to a quiz" flow, not push-to-student).

The second slice, rubric + structured feedback assistance, replaces `Assignment.grading_rubric` — previously a single free-text field fed as raw prose into one holistic AI grading call — with a real structured rubric: `quizzes.RubricCriterion` (`assignment` FK, `name`, `description`, `max_points`, `order`), managed on a new `manage_rubric_view` page via Django's `inlineformset_factory` (the first use of that tool in this codebase — the existing `ChoiceFormSet` is a plain bulk-create formset with no support for editing/deleting existing rows, which criteria genuinely need across repeated teacher sessions). `assignment_ai.py::suggest_assignment_grade` no longer returns one opaque `{"score", "feedback"}` guess; its signature changed to take the criteria list and it now returns `{"criteria": [{"score", "feedback"}, ...], "overall_feedback"}`, one entry per criterion in the same order given — the AI scores and comments on *each part of the rubric*, and the holistic total (`AssignmentSubmission.ai_suggested_score`) is computed in Python as their sum rather than trusted as a single AI guess. Each per-criterion suggestion is persisted as a new `quizzes.CriterionScore` row (`submission`, `criterion`, `ai_score`, `ai_feedback` — deliberately no teacher-editable fields on it) so the breakdown is durable and visible on the grading page, not just a page you had to catch at submission time. Critically, none of this touches the advisory-only architecture the tests already lock in: `grade_assignment_view`'s `GradeAssignmentForm` (`final_score`, `teacher_feedback`) remains the *only* authoritative write path, still pre-filled from the (now-aggregated) AI suggestion and still fully teacher-editable before saving — this feature decomposes *how the suggestion is produced and shown*, it doesn't add a second grading decision. A rubric-less assignment (the common case until a teacher opts in) skips the AI call entirely rather than falling back to the old holistic-guess prompt — a deliberate product decision, not a regression: `suggest_assignment_grade` is now rubric-shaped through and through, so "no rubric" means "no AI assist yet," consistent with `extract_text_from_file` already returning nothing rather than faking a result when it can't do the job properly. Also fixed in passing: the rubric is now shown on `assignment_detail.html` to every viewer, including students — previously invisible anywhere in the app, even to the teacher grading against it. Out of scope for this slice, deliberately: per-criterion teacher overrides (the teacher's one holistic decision is enough for v1), and rubric templates reusable across assignments (criteria stay assignment-scoped, matching how `Question`/`Choice` are quiz-scoped).

The fourth and final slice, teacher insight summaries, turned out to be mostly a wiring-and-safety fix rather than new architecture — `analytics.NarrativeSnapshot` plus `analytics/services.py::create_narrative`/`draft_narrative`/`approve_narrative` (metrics-snapshot freezing, an AI/template toggle, a DRAFT→APPROVED review gate) already existed from the prior roadmap's analytics work, but two things stopped it from being real: `analytics/narrative_ai.py::generate_ai_narrative` built its own raw `anthropic.Anthropic(...)` client instead of using `ai_core.client` — the exact item this session's Phase 0/1 audit flagged as "unverified AI-vs-template status" — with no `AIError` handling anywhere around it, so a Claude failure would 500 the whole narrative-creation request; and only `NarrativeSnapshot.Scope.SCHOOL` was wired to a view, with no per-class narrative and nothing topic-level to narrate (`class_metrics` only has submission rate / academic average — the roadmap's own example, *"3 students need support on Fractions this week,"* isn't computable from `analytics` data at all, since per-student topic mastery lives in `mastery`). Both are fixed now: `generate_ai_narrative` is rewritten onto `ai_core.client.complete_text` matching `dashboard/ai_reports.py::generate_student_report`'s exact conventions, and `create_narrative` now wraps the generator call in `try/except AIError`, falling back to `draft_narrative` and correcting `generation_method` back to `"grounded-template"` on failure — the same graceful-degradation pattern every other AI call site in the codebase already has. New `mastery/services.py::class_topic_bands(school_class, subject, term)` reuses the exact per-student `topic_mastery_for_student` loop `differentiated_tasks_view` already does, aggregated to per-band counts instead of student lists; new `analytics/services.py::class_insight_metrics(school_class, term)` combines `class_metrics` with a `topics_needing_support` list built from that — filtered to only topics where at least one student is in `NEEDS_SUPPORT`, so the narrative payload stays focused on what's actionable rather than dumping every topic's full counts. `analytics/views.py::class_detail` now has its own "Create AI insight summary" button and narrative-drafts card, mirroring the dashboard's existing one exactly — no new review mechanism, `NarrativeSnapshot.clean()` already required `school_class` for `Scope.CLASS` before this pass, so no model change was needed at all. Deliberately out of scope: changing the `ANALYTICS_AI_NARRATIVES` env-var default or introducing a per-school DB toggle (this pass only makes the AI path safe when a deployment turns it on, not who has it on), `Scope.OFFERING` narratives (model already supports it, nothing asked for it), and editing/regenerating an existing narrative (the DRAFT→APPROVED gate stays binary).

**Phase 5 (Teacher Copilot 2.0) is now fully shipped** — all 4 deliverables from the source roadmap (question-bank generation and quality review, differentiated tasks by mastery level, rubric/feedback assistance, and teacher insight summaries) are built, tested, and documented.

## Phase 6 — Suku360 integration

**Goal:** Secure API contract with Suku360; hand off institutional ownership without duplicating it.

Deliverables:

- Define secure API contracts and identity mapping.
- Receive school/class/subject/teacher/learner context from Suku360.
- Send approved learning evidence, mastery summaries, and learning-gap signals to Suku360.
- Idempotency, tenant isolation, audit, integration-failure recovery.
- **Design the "approved evidence" interface `reports` needs before it can stop reading `gradebook` directly** (see audit doc).
- **Design the notification boundary `academics`/`gradebook` need before `communications` can be extracted** (see audit doc).
- Once the contract and boundaries above exist: extract `attendance`, `finance`, `guardians` (low risk), then `reports` and `communications` (need the interfaces above first).

**Status: outbound evidence API and inbound roster sync (v1, read-only) both shipped; the frozen-app extraction itself is still open, pending this sync foundation being proven in practice.** This was genuinely new territory for the codebase — confirmed by exploration before building it: no API framework (no DRF), no token/API-key auth, and no versioned JSON API convention existed anywhere. New `integrations` app adds `IntegrationCredential` (one active, SHA-256-hashed bearer token per school — the plaintext is shown to a `SCHOOL_ADMIN` exactly once at generation time via `credential_settings_view`, regenerating immediately invalidates the old one) and three read-only, `/api/v1/`-versioned endpoints — `evidence/`, `mastery-summary/`, `risk-signals/` — that expose data this codebase already computes, not new computation: `gradebook.evidence.approved_evidence_for_school(school, term)` (a new bulk function added to the *already-designated* `gradebook/evidence.py` interface module — real, if partial, progress on this phase's own named prerequisite, "design the approved evidence interface `reports` needs," without touching `reports` itself, which stays frozen and untouched), `mastery.services.class_subject_mastery` (flattened into plain JSON since the service returns ORM objects embedded in dicts), and `analytics.RiskSignal` (scoped to `OPEN`/`ACKNOWLEDGED`, the same "currently open gaps" scope `analytics.dashboard` already uses internally, not full history). `integrations/auth.py::authenticate_request` is deliberately a separate mechanism from `schools.middleware.ActiveSchoolMiddleware` — that middleware is session/logged-in-user shaped and doesn't apply to a credentialed machine caller; the API always derives `school` from the verified bearer token, never from a request parameter, matching `docs/security-and-tenancy.md`'s explicit invariant that APIs must follow the same tenant-isolation discipline as HTML views (verified directly: a valid credential for one school cannot see another school's evidence, mastery summary, or risk signals, even when passed that school's own class/term ids).

Deliberately out of scope for this slice: the inbound direction (receiving school/class/subject/teacher/learner context *from* Suku360) and any identity-mapping design beyond reusing the existing `School.slug` as the external-facing tenant identifier; idempotency keys, rate limiting, retry/failure-recovery semantics, and pagination (real production-hardening concerns for once an actual consumer exists to design against); multiple credentials or per-credential endpoint scoping (one full-read credential per school for this pass); and, as always, extending or migrating any frozen app (`reports` stays exactly as it was — only the interface it *could* eventually consume was extended).

Investigating the two prerequisites literally named above turned up a surprise: both were already done, verified directly against current code rather than trusted from docs — `reports/services.py` has only ever imported `gradebook.evidence` in this codebase's history visible this session, and `academics`/`gradebook` had zero `communications` imports, already decoupled via signals (`gradebook.signals`'s two domain events plus stock `post_save`/`post_delete` on `academics.models`, both consumed only by `communications/receivers.py`). `docs/repository-audit.md` already recorded both as resolved; `AGENTS.md` line 23 hadn't been updated to match and still listed them as open, now corrected. That check did surface one real, undocumented gap of the identical shape: `quizzes/views.py` and `dashboard/lesson_workflow.py` still imported `communications.services` directly for assignment-submission and lesson-note-review notifications — not covered by the roadmap's `academics`/`gradebook`-only wording, but the same problem. Closed the same way: `quizzes` now relies on a stock `post_save` receiver on `AssignmentSubmission` (the notification content is fully derivable from the saved row, no custom signal needed); `dashboard` gained its own `dashboard/signals.py` (two domain events, `lesson_note_needs_review`/`lesson_note_author_notified`, fired at the exact points the direct calls used to happen, since a lesson note's notification content genuinely depends on *which* state transition occurred and a stock model signal can't distinguish that). `communications/receivers.py` gained three matching receivers reconstructing the identical title/message/target_url/dedup-key strings that were removed — a relocation, not a behavior change, verified with new signal-chain tests in `communications/tests.py` mirroring the existing `GradebookDomainEventReceiverTests` pattern. Net effect: zero remaining keep-side → `communications` imports anywhere for notifications; dependency direction is `communications → academics`/`gradebook`/`quizzes`/`dashboard` everywhere, not the reverse.

This is still the phase that actually separates the frozen apps from this codebase — one outbound API slice is a first concrete step, not a substitute for the inbound sync, the two named interface/boundary prerequisites being finished, or the extraction itself.

**Inbound direction: v1 shipped (read-only roster pull).** `docs/suku360-inbound-sync-design.md` was originally written design-only because "no real Suku360 API exists to integrate against yet" — that premise turned out to be wrong. Suku360 is a real, live, actively-developed system (same owner, separate repo at `C:\Users\boama\suku360`), already referencing Nyansa in its own docs (*"Nyansa or other learning tools may contribute learning evidence, but they do not independently define the official school report card"*). Once that was discovered, the design doc's own reasoning mostly held up, with one real correction: it assumed Nyansa-side work would be enough once a contract existed, but Suku360 turned out to have **zero server-to-server authentication anywhere** (session-cookie-only, system-wide) and no whole-school roster endpoint for a machine caller — so this slice built real new infrastructure on **both** repos, not just Nyansa's side.

On Suku360: a new `domains/integrations/` app — `PartnerCredential` (bearer token, SHA-256-hashed, school-scoped, Django-admin-issued for v1), a new `PartnerTokenAuthentication` DRF class (the first non-session auth mechanism in that codebase), and one endpoint, `GET /api/v1/integrations/roster/`, deliberately *not* nested under `schools/<school_pk>/` like the rest of that API since the caller has no session and therefore no client-supplied school id to even consider trusting — school scope comes entirely from the credential. `docs/19_SECURITY_TESTING_THREAT_MODEL.md` got a new threat-scenario entry per that document's own stated maintenance rule.

On Nyansa: `suku360_id` added to `School`, `SchoolMembership`, `SchoolClass` as the design doc's §4 proposed — but *not* to `SubjectOffering` as originally guessed; Suku360's `TeachingAssignment` already includes the teacher, so the natural match turned out to be `TeacherAssignment` instead (deliberately non-unique there, since Suku360 scopes a teaching assignment per academic year while Nyansa scopes it per term). New `integrations.SyncBatch`/`SyncRecord` match the design doc's §8 proposal closely. New `integrations.Suku360RosterCredential` stores the token *Suku360* issued to Nyansa — the opposite direction and shape from `IntegrationCredential` (plaintext, not hashed, since it has to be replayed outbound). `integrations/suku360_sync.py::pull_roster` does the actual upsert, reusing `roster_import.py`'s account-creation conventions for newly-seen people; `pull_suku360_roster` is a plain management command, matching `billing`'s `generate_license_invoices` convention (no Celery/cron infra exists on either side).

Deliberately still out of scope: Nyansa evidence/mastery reaching Suku360's UI (confirmed by direct inspection that Suku360's `learner_success`/`intelligence` domains have no ingestion point for an external signal — needs new Suku360-side modeling, not just an endpoint); two-way write-back; enforcing read-only-in-Nyansa-UI for already-synced fields; reconciliation for schools with pre-existing, pre-sync data (a first sync will create duplicate classes/memberships rather than matching by name); periodic re-sync (documented but commented-out in `render.yaml`, pending Render's paid tier); and the frozen-app extraction itself, which still needs this sync foundation proven in practice first.

**Premium gating + automated handoff (v1.1), shipped before either v1 commit was pushed.** Before pushing, the integration was scoped to Suku360's Premium subscription tier, and the token handoff was automated end-to-end. `SchoolBillingPlan.tier` (`STANDARD`/`PREMIUM`) lives on Suku360's existing billing model rather than a new entitlement system; `RosterView` re-checks it live on every request, so a downgraded school loses access immediately (proven live, not just asserted: downgrading a test school mid-session turned its still-active token's next request from 200 to 403). Issuing/rotating a `PartnerCredential` in Suku360's admin now POSTs the new token straight to a new Nyansa webhook (`POST /suku360/webhook/credential/`, HMAC-SHA512-signed with a shared `SUKU360_WEBHOOK_SECRET`, same scheme as the existing Paystack webhooks), which upserts `Suku360RosterCredential` and runs `pull_roster` automatically — no one has to copy a token by hand or run the management command for the first sync. That push had to be deferred with `transaction.on_commit(...)`: calling it inline raced Nyansa's callback fetch against Suku360's own still-open admin transaction, reproduced live as a spurious 401 before the fix. Proven end-to-end with two real dev servers and an actual admin form submission, not just mocked. The one remaining manual step is inherent, not a shortcut: which Suku360 school maps to which Nyansa school has no automatable source of truth until a human sets it once.

**Single sign-on handoff (v1.2).** The roster sync creates Nyansa accounts with `set_unusable_password()` — dormant until now. A "Launch Nyansa" button in Suku360's sidebar (headteacher/teacher/student only — the three roles with a real Nyansa counterpart) POSTs to a new `domains/integrations/` endpoint, which mints a short-lived (60s) HMAC-SHA512-signed token — reusing `SUKU360_WEBHOOK_SECRET`, no new secret — and hands back a Nyansa URL. Nyansa verifies the signature, checks a single-use nonce (`integrations.SsoNonce` — closes the replay window a leaked/logged URL would otherwise leave open, proven live: reusing the same link a second time returns 401 instead of a second login), resolves or just-in-time creates the matching account, and logs it in. The identity claim genuinely differs by role, caught by reading the actual models rather than assumed: a Suku360 teacher's claim is their `User.id` (matches how the roster sync already stores it), but a student's is their `Student.id` — a separate, nullable-linked academic-record id, not their login `User.id` — verified live against real data, not just asserted, including that an SSO login correctly reuses an already-roster-synced teacher account instead of creating a duplicate. Deliberately not full OAuth2 — disproportionate infrastructure for a two-system partnership already using this HMAC pattern elsewhere.

## Phase 7 — Offline & low-bandwidth learning

**Goal:** PWA caching, offline practice queue, low-data modes.

**Status: all 3 deliverables shipped — PWA caching, an offline practice queue for quiz submissions, and a low-data mode for materials.** Picked up ahead of the rest of Phase 6 because the two items still open there (inbound Suku360 sync, frozen-app extraction) are both blocked on a real Suku360 API contract that doesn't exist yet — building either now would mean coding against a guessed contract, the exact risk `docs/suku360-inbound-sync-design.md` was written to avoid. Phase 7 has no such external blocker. This was greenfield: no PWA/service-worker/manifest infrastructure existed anywhere in the codebase before this pass.

**Scope boundary decided up front**: Tutor's `PRACTICE` mode (`tutor/engine.py`) calls the live Anthropic API for every message, including generating each question — it cannot function offline under any design. "Offline practice queue" therefore means the deterministic `Quiz`/`Question` flow, the only practice content in the codebase that doesn't require a live AI call, not the Tutor.

PWA caching adds `static/manifest.json` (icons reuse the existing logo/favicon SVGs — no new asset generation) and a service worker registered from `base.html`. The service worker's source lives at `templates/service-worker.js` — a Django **template**, not a plain static file, specifically because production static assets are served through `whitenoise.storage.CompressedManifestStaticFilesStorage`, which content-hashes filenames; a service worker with hardcoded `/static/css/style.css`-style paths would silently 404 after every deploy. Rendering it through `config/views.py::service_worker_view` with `{% static %}` resolving each precached URL keeps it correct in dev and prod with no build step, and the view is routed at `path("service-worker.js", ...)` directly in `config/urls.py` (not nested under any `include()`) since a service worker's default scope covers only the directory of the URL that serves it — root scope needs a root route, and WhiteNoise as configured only ever serves paths under `/static/`. The worker precaches the app shell and does cache-first for static assets. Page navigations are always fetched from the network, falling back only to the generic, non-personalized `static/offline.html` shell — **not** to a cached copy of the requested page itself. A security review after this phase shipped caught that the original design (caching and replaying the last-seen response per URL) would have let one student's cached dashboard, grades, or quiz result be served to whoever logs in next on the same shared device if the network happened to fail at that moment — a realistic scenario on the shared lab computers this feature targets. Fixed by never caching or replaying authenticated navigation responses at all, bumping `CACHE_NAME` to purge anything already cached under the old scheme, and clearing all Cache Storage client-side on logout (`templates/base.html`'s logout form) as defense in depth.

The offline practice queue is entirely client-side (`static/js/offline-queue.js`) — no new model, no new status field. `quiz_take_view`'s deadline and `max_attempts` checks already run unconditionally before the POST branch and both silently redirect back to `quiz_start` on failure (no distinguishing status code, and Django's `messages` framework is invisible to a background `fetch()` replay anyway), so the queue has to infer the outcome from the response's final URL after redirect-follow: `/quizzes/result/...` means success, landing back on `/.../start/` means rejected (deadline or attempts exhausted — the view collapses both into the same redirect, so the client can't tell which), anything else means still offline and stays queued. `window.addEventListener('online', replayQueue)` is the primary trigger (works everywhere, including Safari, which has no Background Sync API) — a queued item is never silently dropped; a rejection surfaces an explicit banner telling the student to check with their teacher. `quiz_take.html`'s submit handling was refactored so both the manual submit button and the existing timer-driven auto-submit-at-zero call go through the same `submitQuiz()` function (calling a form's own `.submit()` from JS bypasses the `submit` event entirely, so the timeout path needed the same fetch-based treatment, not just the button). Getting the replay's CSRF token right took a real correction: `CSRF_COOKIE_HTTPONLY = True` already in `config/settings.py` means JavaScript cannot read the `csrftoken` cookie at all, so the initial cookie-reading approach would have made every replayed submission fail CSRF validation. Fixed by exposing the token instead via `<meta name="csrf-token" content="{{ csrf_token }}">` in `base.html` (Django hardcodes the `csrf` context processor for any `RequestContext`-rendered template regardless of the `TEMPLATES` setting's explicit processor list, so this needed no settings change) and reading that meta tag instead of the cookie.

Low-data mode reuses `courses/study_ai.py::get_or_extract_material_text` — already-cached PDF text that previously only ever fed AI summaries/Q&A, never shown to a student directly. A new `courses/views.py::material_text_view` (same enrollment/teacher permission check as `subject_detail_view`) renders it as plain text; `subject_detail.html` now renders both a Download link and a View as Text link per material, toggled by a `localStorage`-backed nav control (`static/js/low-data-mode.js`) that sets `data-low-data` on `<body>` — pure client-side preference, no new DB field, consistent with the queue's own "no new model" approach. `StudyDocument` needed no equivalent change: its student-facing templates never exposed a raw-file download link at all (only the AI summary and Q&A chat), confirmed by direct inspection rather than assumed. Video materials (`Material.material_type == VIDEO`) keep their plain external link — no offline/low-bandwidth story for video, deliberately deferred.

Deliberately out of scope for this phase: caching any AI-backed page (tutor, summaries, feedback — these need a live call and can't be meaningfully cached); a fix for the pre-existing race where two devices could each pass the `attempts_used` check before either commits; separating "deadline passed" from "attempts exhausted" in the rejection message (the view already collapses both into one redirect — distinguishing them is a server-side change); an offline queue for `Assignment` submissions; upload size/type limits or compression (a separate concern from bandwidth-of-consumption); and any persisted server-side preference for low-data mode (kept in `localStorage`, matching the phase's "no new DB model" pattern throughout).

## Phase 8 — Scale & commercialisation

**Goal:** Licensing/usage tiers, individual learner accounts, cost controls, security review.

**Status: 3 of 4 deliverables shipped.** The user made three business calls this session: individual (non-school) learner accounts stay out of scope — Nyansa's whole architecture is school-first, and exploration found it's more than a schema question anyway (self-signup already produces a schoolless `User` today, but nearly every content view assumes `request.school`, and a few — `TutorSettings.objects.get_or_create(school=request.school)` against a non-nullable FK — would hard-crash for one); Paystack is the payment provider for licensing, reusing the platform's existing `PAYSTACK_SECRET_KEY`; pricing tiers were left to be proposed rather than specified, explicitly as a starting placeholder to tune later, not researched final numbers.

Security review and cost controls are both shipped. The security review ran the `security-review` skill against `docs/security-and-tenancy.md`'s existing standard, scoped to the newest/highest-risk code from this session, and caught two real bugs: `quizzes/views.py::quiz_take_view` never checked `quiz.status`, so a student who guessed a DRAFT (unreviewed AI-generated) quiz's numeric ID could bypass the `QuizGenerationSettings.require_review` gate entirely and get a real graded `Submission` — fixed by adding the same check `quiz_start_view` already had. The Phase 7 service worker also cached and replayed authenticated navigation responses (dashboards, grades, quiz results) keyed only by URL with no per-user scoping or logout cleanup — a real risk on the shared school lab computers that phase explicitly targets — fixed by never caching/replaying authenticated pages at all (falling back only to the generic `offline.html` shell) and clearing Cache Storage client-side on logout. Adding CI dependency scanning (`pip-audit`, none existed before) as part of the same pass then surfaced that `requirements.txt` had drifted from what was actually installed and tested locally: `pypdf`, `Markdown`, `python-dotenv`, and `xhtml2pdf` were all pinned to versions with known vulnerabilities that a fresh install (the production Docker build) would still pull — `pypdf` mattered most, since it parses untrusted, user-uploaded PDFs. All four bumped to current patched releases.

Cost controls had almost nothing to build on: only `tutor` logged any AI usage at all (`TutorUsageEvent`), and only as an unread token count — the other 7 AI call sites (`courses/study_ai.py`, `quizzes/ai_quiz_generator.py`, `quizzes/ai_grading.py`, `quizzes/assignment_ai.py`, `dashboard/lesson_ai.py`, `dashboard/ai_reports.py`, `analytics/narrative_ai.py`) logged nothing whatsoever. `ai_core` — previously a plain Python package, not even a registered Django app — now owns a new `AIUsageEvent` model and logs every one of those 7 sites' calls, since they all already funnel through `ai_core.client.complete_text`/`complete_json`. `school` is threaded through each call site: derived internally from an already-passed object where one exists (`create_bank_questions(subject, ...)`, `generate_student_report(student, subject, ...)`), or added as an explicit `school=None` keyword param threaded from the calling view otherwise — chosen per-site specifically to avoid a redundant parameter that could drift from the true value where a trustworthy source already exists. A new `ai_core/pricing.py` estimates USD cost live from token counts (never frozen at call time, so a correction to the pricing table applies to historical rows too) and returns `None` for an unrecognized model rather than guessing. A new school-admin-only `/ai-usage/` report (`ai_core/views.py::ai_usage_report_view`) shows the current month's calls/tokens/estimated cost broken down by feature. One platform-wide, env-configurable daily token cap (`AI_DAILY_TOKEN_CAP_PER_SCHOOL`, generous default) is enforced centrally in `ai_core.client.complete_text` before the API call is even made — a protective ceiling against runaway/bugged usage, not a considered business limit, and deliberately not a per-school-configurable policy, which would need the same business input still pending for licensing tiers. Every one of the 7 sites already had `try/except AIError` graceful-degradation handling from Phase 2, so a cap-exceeded `AIError` needed zero new UI work anywhere. `tutor`'s own separate usage/quota mechanism is untouched — unifying working, independently-tested code into the new shared model for no immediate benefit was deliberately out of scope.

Licensing/usage tiers is now shipped too, as a new `billing` app — schools paying Nyansa, the opposite direction from `finance` (students/guardians paying the school). `finance` is a frozen app slated for extraction to Suku360, so `billing` (permanent Nyansa revenue logic) deliberately does not import from it — `billing/gateways.py::PaystackGateway` is a small, structural duplicate of `finance.gateways.PaystackGateway` (same Paystack account, via the same `PAYSTACK_SECRET_KEY`, independent code) rather than a shared import, since a future `finance` extraction must never be able to break Nyansa's own billing. `LicensePlan`/`SchoolLicense`/`LicenseInvoice`/`LicensePayment`/`BillingProviderEvent` mirror `finance`'s `Payment`/`ProviderEvent` shapes and its exact webhook signature-verification/idempotency/reconciliation discipline from `docs/security-and-tenancy.md`'s payment security rules. A `LicenseInvoice`'s AI-usage line item reuses `ai_core.services.school_ai_usage` directly rather than recomputing anything. Three starting plans were seeded via data migration (editable afterward through Django admin, not hardcoded in Python): Starter (GHS 500/month, Learning Workspace only, no AI passthrough), Standard (GHS 1,500/month base + AI usage at cost + 20%, unlocking Tutor/Teacher Copilot/Mastery/analytics narratives), and Partner (priced per partnership, unlocks the Suku360 integration). These are explicitly a starting proposal, not researched final pricing.

Two real bugs were caught and fixed while building this, both before ever reaching the user: `ai_core.pricing` estimates AI cost in USD, but the first cut of `generate_invoice` added that figure straight into a GHS invoice with no conversion — silently treating USD as GHS. Fixed with an explicit, env-configurable `AI_USAGE_USD_TO_GHS_RATE` (also a placeholder, not live FX data). And `initiate_license_payment` was originally wrapped in `@transaction.atomic` exactly like `finance.services.initiate_mobile_money` — mirroring that pattern faithfully turned out to reproduce a latent bug never caught there because no `finance` test exercises the gateway-failure path: re-raising an exception after an internal `try/except` updates a row to `UNKNOWN` rolls back the *entire* atomic block on the way out, silently discarding the row instead of preserving it as documented. Fixed in `billing` by not wrapping the function in `atomic()` at all (an external network call was never safe to put inside one); `finance` itself was left untouched since fixing a latent bug nobody asked about there would have been scope creep beyond this pass.

Deliberately out of scope for this slice: feature-gating enforcement (a school without a paid/active plan isn't locked out of anything today — this ships the billing *mechanism*, not access control); proration, mid-period plan changes, refunds, annual billing, multi-currency; wiring `generate_license_invoices` to an actual scheduler (no Celery/cron infrastructure exists anywhere in this codebase to hook into — it's a plain management command, same as every other recurring job here, meant to be triggered externally).

**Phase 8 is now 3/4 complete** — security review, cost controls, and licensing/usage tiers are shipped; individual learner accounts remains open, by the user's own choice, pending it becoming an actual product direction.
